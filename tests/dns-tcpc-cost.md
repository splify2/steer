# Приёмка 2.x: память TCP-клиентов DNS после пика

**Что измеряем.** Самостоятельный `steerd dnsd`, один и тот же локальный TCP
upstream, короткий корректный A-запрос `slot.test`. Пустой список каналов;
нет `dns.other`, reload, таблицы fake-IP или маршрутов по ответам. Все вопросы
доходят до fixture: он проверяет вопрос, возвращает A `192.0.2.42` с TTL 0;
клиент проверяет всю DNS-запись и исходный ID. В работе не более одного вопроса
наверх одновременно, чтобы не платить за рост *другой* таблицы TCP (`tcpu`).

**Один прогон** создаёт частные PID/mount/net namespaces с единственным `lo`;
`/run`, `/etc`, `/var`, `/tmp` временные. Дальше обычный UID 65534 без
повышения привилегий. По одному новому PID на каждую ступень (1, 100, 1000),
два цикла одного размера на этом PID. Унаследованный NOFILE только понижается
до 4096: штатный предел при этом 1024 клиента. Ни одного дополнительного
соединения сверх выбранной ступени на пике. Между последовательными
подключениями/ответами пауза не менее 2 мс. Это измерение числа удерживаемых
клиентов, не тест предельного QPS или длины очереди listen.

* `baseline`: один прогревочный обмен и контроль задержки, затем без клиентов.
* `before`: контроль задержки перед набором ступени; память и FD без клиентов.
* `during`: настоящие одновременно открытые **принятые** сокеты. Проверяется
  соответствие множества клиентских портов записям ESTABLISHED c локальным
  портом DNS, inode которых есть у данного PID. Каждый из N клиентов получил
  ответ; после измерения задержки и тихого окна все N повторно подтверждены.
* `after`: клиенты не закрывают сокеты первыми. После последнего тихого окна
  даются ещё 12,5 с (`TCP_IDLE_SEC=10` плюс секундный тик и запас); проверяются
  ноль принятых, FD как на baseline и EOF у **каждого** клиента. Затем вновь
  снимается контроль задержки. Точно так же проходит второй цикл.

`rss_kib`, `pss_kib`, `anon_kib` — `smaps_rollup` только проверяемого PID, FD —
его `/proc/PID/fd`, без клиентского процесса, fixture и памяти сокетов ядра.
Задержка — p50/p95 (мкс, ближайший ранг) 40 одинаковых RTT по уже открытому
TCP, с интервалом 5 мс; на пике это один из N клиентов. Время подключения не
входит в RTT. `fill_cpu_ms` — всё CPU-время основного потока DNS по `schedstat`
за набор N с ответами; `quiet_cpu_us` — его время исполнения за отдельное
окно 2,2 с без вопросов. Это не профилировщик отдельных функций. Логи JSONL
хранят также время набора, счётчики, PID и SHA-256 проверенного ELF.

## Повторить

Из worktree стенда, передать два чистых checkout и **одинаковые** настройки
компилятора. В приёмке использован GCC 13.3, native x86_64, базовый профиль
Makefile `-O2 -Wall -Wextra`, `REV=tcpc-audit`, без перехвата allocator и
отладочных флагов. Пуски последовательные, на одной паре CPU.

```sh
OUT=$(mktemp -d /tmp/opencode/tcpc-repeat.XXXXXX)
for pair in "v214:$V214_TREE" "current:$TREE_7CD1022"; do
    label=${pair%%:*}; tree=${pair#*:}
    make -C "$tree" CC=gcc BUILD="$OUT/$label-bin" REV=tcpc-audit \
        "$OUT/$label-bin/steerd" >"$OUT/$label-build.log" 2>&1 || exit 1
    taskset -c 0,1 sh tests/dns-tcpc-cost.sh "$OUT/$label-bin/steerd" \
        >"$OUT/$label.jsonl" 2>"$OUT/$label.err" || exit 1
done
```

Требуются Linux с `smaps_rollup` и `schedstat`, права для `unshare`/`mount`,
`ip`, `setpriv`, Python 3. На другой машине заменить `0,1` доступной парой
для **обоих** запусков. Стенд не входит в обычный `make test`.

## Как отличить резерв от накопления

У `v2.1.4` и `7cd1022` в измеренной ABI `sizeof(struct tcpc) = 4336` байт
(DWARF отдельного объекта `proxy.o`, в том числе 4098 байт входного буфера).
Резолвер выбирает место *перед* `accept`: при опустевшей очереди может быть
выделен ещё один свободный слот. После прогрева на одном клиенте это примерно
два слота и ёмкость массива в 16 указателей. Для последовательного набора
ещё 99 или 999 слотов ожидаемая прибавка полезной ёмкости, включая рост
массива указателей до 128 или 1024, — **420,1 и 4238,0 КиБ**. Это расчёт,
а не замер RSS: он не включает метаданные malloc, округление до страниц
и остальную память резолвера.

На `7cd1022` см. `src/dnsd/proxy.c`: `tcpc_pick` (2109) сначала ищет свободный
слот; `tcp_accept` (2137) использует его повторно; `tcpc_close` (1712)
закрывает FD и освобождает выходной буфер, но сохраняет сам слот. На тике
`tcp_reap` (2230) просматривает таблицу до достигнутого размера. Наличие
таблицы само по себе не требует постоянного тика: когда нет работы, ожидание
в `run_proxy` может стать бессрочным. Таблица освобождается в `tcp_close_all`.
Соответствующие функции в `v2.1.4` работают так же.

Два равных пика проверяют повторное использование в заданном диапазоне.
Сравнивать следует разности внутри одного PID, особенно анонимные страницы:
PSS разделяемых страниц зависит и от посторонних процессов на машине.
Задержки и CPU включают обычную обработку DNS; по ним нельзя выделить
стоимость одной проверки слота или вывести асимптотику экспериментально.

## Результат на Linux 6.8.0-149-generic, x86_64

Разность относительно прогретого baseline того же PID после штатной уборки.
В каждом цикле число попыток, одновременно принятых сокетов, проверенных
ответов и полученных EOF совпало с размером ступени.

| Клиентов | Остаток RSS, обе версии, цикл 1 / 2 (КиБ) | Остаток PSS, v2.1.4, цикл 1 / 2 (КиБ) | Остаток PSS, 7cd1022, цикл 1 / 2 (КиБ) | FD до / пик / после, обе версии |
|---:|---:|---:|---:|---:|
| 1 | 0 / 0 | 0 / 1 | 0 / 0 | 9 / 10 / 9 |
| 100 | 420 / 420 | 420 / 420 | 420 / 420 | 9 / 109 / 9 |
| 1000 | 4256 / 4256 | 4256 / 4255 | 4256 / 4256 | 9 / 1009 / 9 |

На 1000 клиентах вся прибавка RSS пришлась на анонимные страницы. Второй
равный пик не увеличил остаток ни у одной версии. В тихих окнах по 2,2 с
после уборки `schedstat` не зарегистрировал времени CPU у основного потока.
При наборе 1000 клиентов он затратил 130,0 / 131,6 мс за два цикла у
v2.1.4 и 125,7 / 120,5 мс у 7cd1022.

На той же ступени p95 RTT (мкс: baseline / после первого / после второго)
составил 238 / 281 / 243 у v2.1.4 и 324 / 258 / 383 у 7cd1022.
Устойчивого замедления после повторного пика не видно, но 40 запросов на
фазу и два цикла не доказывают эквивалентность задержек. Вывод для ревью:
удержание памяти до достигнутого максимума подтверждено уже в v2.1.4;
добавочного накопления или регрессии по памяти и FD в 7cd1022 не наблюдали.
