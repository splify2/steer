# Цена локального `plugin install` и первого `status` после обрыва

**Результат.** Для net1/VLESS с 8 МиБ пользовательских данных в старом дереве
`544b31a` тратит на обновление **75,54 / 78,99 мс** (p50/p95), против **16,21 /
18,26 мс** у `515a463`. До решения он проверяет оба поколения. После обрыва первое
чтение занимает **60,03 / 64,08 мс**, последующее — **3,70 / 4,26 мс**.
На уже журнальной файловой группе существенного дополнительного сдвига медианы
в этой точке не видно: **70,62 → 70,19 мс**. [Полная таблица](pluginmgr-cost-results.md).

Это измерение Linux legacy CLI в offline-режиме. Две группы по два подписанных архива:
`files` — net1 и VLESS как обычные файлы данных, без регистрации библиотек/видов;
`net1` — те же ELF как библиотека и программа с зависимостью, видом, helper/check и
подкомандами VLESS. Реальные байты A → B меняются у обоих участников. Имена ELF,
их полные SHA-256 и версии приведены в `pluginmgr-install-cost.py`; обе программы
сообщают 2.1.4, net1 меняется с 1.5.0 на 1.6.0. Кроме ELF есть по 24 небольших
подписанных файла на участника. Манифесты net1/VLESS основаны на примерах SDK
`fa2b823d928f6bdd3f1b4a533a0b2cb874b4f4dd`, без внешних системных зависимостей.

### Что сравнивается

- Три свежие stripped shared-сборки `build/build-libs.sh`: тег `v2.1.4` (`70d11ebb`),
  `515a4633`, `544b31a9`. Одна VM, GCC 13.3.0, binutils 2.42, glibc 2.39, layout 2.1,
  `STEER_OPT=split` (`-Os` у менеджера, `-O2` у горячих файлов), клиентские wolfSSL
  5.9.4 и ngtcp2 1.25.0-2, одинаковые исходники зависимостей и флаги рецепта. В
  каждой строке свой `steerd` и соответствующая `libsteer.so`; `/etc/ld.so.cache`
  внутри mount namespace выбирает общую пару wolfSSL/ngtcp2 из `544b31a`, в том
  числе когда manager меняет `LD_LIBRARY_PATH` для пробы ELF. Фактические пути,
  версии и хеши менеджеров есть в JSONL. Порядок аргументов одинаков, библиотека первой.
- `*` в таблице: у тега нативная ось crypto **1.0**, не 2.0. В основной серии для
  одинакового входа и загруженной crypto-пары всем передаётся стендовый
  `STEER_PLUGIN_CRYPTO=2.0`. Это сравнение кода менеджеров. Без подстановки и
  со штатными библиотеками тег отвечает на новый net1 `plugin.compat_needs_core`
  (`^2.0`, `have: 1.0`); времени «успешного штатного обновления» здесь нет.
  Отдельный контроль `native` измеряет поддержанное обновление `files` у тега с
  его собственными тремя `.so` и без переопределения оси.
  Например, при 8 МиБ там **13,82 / 14,79 мс** против **13,56 / 14,38 мс** в общей серии.
- `update` — только успешная команда установки двух файлов. `recovery` — только
  первый отдельный `status --json` со всеми его штатными проверками. Подготовка —
  один и тот же `state2` из существующего стенда: `SIGKILL` после второго rename
  реестра, до решения; это *не* часть таймера. Архивы убраны с исходных путей.
  `clean` — немедленно следующий отдельный `status` без журнала. У тега журнала
  группы нет; у `515a463` он есть только для `files`. Их неподдержанные recovery
  не заменялись быстрым чтением смешанного состояния. Одиночная установка здесь не измерялась.
- Один детерминированный **публичный тестовый** ключ, неизменные байты USTAR/gzip
  и проверка подписей менеджером. До таймера восстанавливается одинаковый исходный
  префикс с фиксированными `state.json`/`keep.d`. В старом дереве первого участника:
  48 мелких пользовательских `.conf` и один несжатый, не разреженный обычный файл
  **4 КиБ / 8 МиБ / 64 МиБ**; отдельно — пользовательский конфиг под `etc/conf`.
  При recovery сверяются SHA-256 обоих деревьев, inode большого конфига, байты и режим
  реестра/keep. При успехе проверяются SHA обоих целевых ELF. Во всех случаях внешний
  конфиг должен остаться. В `stream` локальный конфиг 4 КиБ, в **каждом поколении**
  первого файлового пакета ещё один подписанный малосжимаемый файл 63 МиБ:
  так входное чтение gzip и чистый `status` тоже проходят большой файл. Это размер
  опыта, а не задокументированный предел пакета.

### Как измеряли

VM KVM, AMD Ryzen 9 7950X3D, 8 vCPU, 15 ГиБ RAM, Linux 6.8.0-149-generic, страница
4096 байт. Один процесс установки за раз. Изолированные mount/PID/net namespaces,
только `lo`, UID 65534, отсутствующий ctl/init.d. Префикс один на выделенной tmpfs
512 МиБ с `noatime`; архивы, исходный снимок, метрики и stdout вне неё. Это
сравнение тёплого page cache и цены CPU/памяти/ёмкости. **Нет** cold boot, сброса
кэшей, сетевого трафика или оценки стоимости `fsync` на флеш/overlay.

На комбинацию — 1 прогрев и 20 измерений, каждый раз новый процесс. Порядок
комбинаций перемешан фиксированным seed в каждом раунде. Распаковка **самим
менеджером** и его дочерние пробы внутри wall; сборка, создание ключа/архивов,
копирование исходного состояния, обрыв, проверки результата и агрегация снаружи.
`CLOCK_MONOTONIC`: от разрешения уже созданному минимальному дочернему процессу
вызвать `execv` до возврата `waitid(WEXITED)`; ожидание завершения наблюдателя не
прибавляется. Wall p50/p95 — 10-я и 19-я из 20 упорядоченных величин.

`RSS max` — максимум Linux `wait4.ru_maxrss` за 20 запусков (максимум отдельного
процесса, с учётом завершившихся потомков, не сумма). `Σ max` — дополнительная
выборочная сумма RSS менеджера и видимых потомков (`/proc/*/statm` и `children`),
с повторным счётом общих страниц, не PSS. Наблюдатель закреплён на vCPU 0, manager
и его потомки — на vCPU 1; после каждого опроса пауза 250 мкс. Ядро и VM не
изолированы от планировщика; короткие дочерние процессы и короткие файловые пики
могут не попасть в выборку. `samples`, максимальный интервал, исходное/конечное
занятое место и отдельные повторы записаны в JSONL. `rchar/wchar=-1` означает
недоступный `/proc/<pid>/io` при замере, а не отсутствие чтения/записи.

`FS на входе / Δпик` — исходная занятость тома и максимальный наблюдавшийся
прирост `(f_blocks-f_bfree)*f_frsize` относительно входа **этой операции**;
учтены также границы до/после. Для recovery на входе уже лежат оба поколения.
Это занятые страницы файлов tmpfs, не размер архива и не память inode/dentry.
Пик префикса и RSS нельзя складывать в оценку флеш или RAM устройства.

Основная серия: 720 измерений, 8–1261 опрос на операцию. Медиана максимального
интервала опроса — 0,390 мс, худший интервал — 4,007 мс. Load average (1 мин)
между началом и концом: 1,43 → 2,04. Квантили эмпирические; 20 запусков не
характеризуют редкие задержки, а различия порядка десятых долей мс не служат
доказательством ускорения. Подготовка и проверка снимков прогревают данные.

### Откуда берётся разница

`pm_group_publish` вычисляет идентичность старых и новых деревьев до публикации.
`pm_group_finish(accept)` проверяет их снова перед решением. При восстановлении
`member` делает два прохода: сначала проверяет **всех** участников, затем снова
проверяет их положение при обратных rename. Поэтому обычный локальный файл размера
S в старом дереве добавляет **2S байт в хеширование** как при update, так и при
recovery (по путям кода, не счётчик физического I/O). Для каждого имени добавляются
`lstat`, проверка mount, для каталога — сортировка/обход. В legacy до G1 таких
проходов нет. У пары дополнительно запускаются загрузчик и ABI-проба staged и
установленной программы. `status` без маркера хеширует файлы из `MANIFEST`, а не
пользовательские дополнения. Поэтому его время почти не зависит от 4 КиБ / 8 МиБ /
64 МиБ *локального* файла. `fingerprint` использует потоковый `pm_file_sha256` с
буфером 64 КиБ. Реестр и `keep.d` небольшие и фиксированные в этом опыте; их
байтовые снимки, напротив, читаются целиком.

При 64 МиБ на паре цена решения видна по wall: `update` **403,28 / 413,64 мс**,
`recovery` **382,60 / 388,73 мс**, но максимальный `ru_maxrss` update — **3,88 МиБ**,
столько же, сколько при 4 КиБ. Пик прироста занятого места на update — **720 КиБ**
при всех трёх размерах, против **680–684 КиБ** у `515a463`. Это **сверх** старого
дерева: `rename` сохраняет его целиком до решения, но не делает ещё одну копию 64 МиБ.
При recovery уже занято **67 120 КиБ**, а сверх этого наблюдали до **4 КиБ**.

**Большой подписанный файл дал другой профиль.** В серии `stream` архив B первого
участника занимает 66 262 124 байта. У `544b31a` update **1323,76 / 1347,72 мс**,
пик RSS **66,62 МиБ**, наблюдаемый прирост тома **65 228 КиБ**. У тега RSS
тоже **66,50 МиБ**: это не копия файла в памяти журнала. `untar_gz_file`
отображает весь *сжатый вход* через `mmap`, а распаковщик последовательно касается
его страниц. При плохо сжимаемом входе эти резидентные страницы учитываются в RSS.
Первое восстановление на `544b31a` — **938,28 / 988,85 мс, 3,62 МиБ RSS**;
чистый `status` — **188,69 / 201,84 мс, 3,38 МиБ RSS**. Здесь он обязан прочитать
и хешировать 63 МиБ из старого `MANIFEST`. Нового отказа по размеру в выбранных
точках не было. Эти значения не устанавливают максимум файла, бюджет или прогноз
задержек на устройстве.

**Файлы пользователя.** При recovery на каждом размере вернулись 49/49 внутренних
файлов, включая прежний inode большого файла; внешний `etc/conf/site.conf`
сохранился. При успешной замене 0/49 внутренних файлов остались в новом дереве
на **всех трёх** ревизиях, 1/1 внешний сохранился. Это различие между откатом и
переносом пользовательских данных: архив B не содержит `local/`, а принятое старое
дерево удаляется при уборке. G1 не добавляет миграцию конфигов при успехе.

### Повторить

В отдельном каталоге `R` разместить три чистых checkout в `v214`, `file`, `core`
на указанных SHA. `WOLFSSL_DIR` и `NGTCP2_DIR` — деревья исходников для обычной
сборки. `A` и `B` — каталоги с известными ELF из [стенда приёмки пары](pluginmgr-net1-group.md);
`SDK` — checkout с указанным объектом; `TESTS` — каталог этих тестов. Для измерителя
нужны gcc, Python ≥3.11 с `cryptography`, `ldconfig`, `setpriv`, `unshare`, доступ к
CPU 0,1 и право создать namespaces и tmpfs.

```sh
export CC=gcc AR=ar JOBS=6 STEER_OPT=split LIBS='-lpthread -ldl -lm' WOLFSSL_DIR NGTCP2_DIR
for v in v214 file core; do
  (cd "$R/$v" && sh build/build-libs.sh "$R/bin-$v" "$(cat VERSION)" "$(git rev-parse --short HEAD)") \
    >"$R/build-$v.log" 2>&1 || exit 1
done
A="$R/bin-v214"; B="$R/bin-file"  # в данном прогоне хеши совпали с закреплёнными ELF
for mode in main native stream; do
  sh "$TESTS/pluginmgr-install-cost.sh" "$R/bin-v214" "$R/bin-file" "$R/bin-core" \
    "$A" "$B" "$SDK" "$mode" >"$R/$mode.jsonl" || exit 1
done
for mode in main native stream; do
  python3 "$TESTS/pluginmgr-cost-summary.py" <"$R/$mode.jsonl"
done
```
