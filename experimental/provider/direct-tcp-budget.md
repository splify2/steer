# Full managed v3 на Linux: 100 и 1000 живых direct TCP-реле

Опция запуска Full `--direct-tcp-clients 100` или `--direct-tcp-clients 1000`
задаёт **общий** предел входов SOCKS5 CONNECT и VLESS plain TCP, не предел
каждого входа. Без опции у Full и Nano по-прежнему 32. Nano отвергает опцию.
Пример: `steer-prototype-hy2-wg-netns --config spec.json --control ctl.sock
--state-dir state --direct-tcp-clients 1000`. `STATUS.tcpClientLimit` показывает
выбранный предел. Apply не меняет бюджет: его задаёт владелец процесса при старте.

В расширенном профиле на запуске и при смене поколения допускается только
v3 с TCP-входами SOCKS/VLESS, маршрутами direct/block, без named outbound,
SOCKS UDP и WG device. Это не матрица комбинаций протоколов.

### Что пришлось увеличить

* На N удерживаемых реле приходится 2N TCP-дескрипторов, 2N native streams
  и обёрток, до N живых route streams на поколение. Предел native binding
  увеличен на **две ссылки** за каждое дополнительное реле (обёртка и guard).
  Открытий маршрутов одновременно по-прежнему до 32; лимит числа потоков не
  обещает 1000 параллельных handshake. Резолвер — 2 worker / 64 jobs.
* В Full opt-in стабильные адреса клиентских слотов обеспечивает `calloc` в
  куче, а не стек на 1000 клиентов (`sizeof(struct client)` здесь 2416 байт).
  Буферы выделяются только при приёме. На поток два направления по 4 КиБ
  вместо штатных 16 КиБ: при N=1000 это 7,81 МиБ полезных буферов плюс
  2,30 МиБ под слоты. Это не полный RSS. Native I/O ограничен 2N операциями,
  backend — 2N+64, in-flight bytes у каждого не более `2*N*4096`.
  Пока предыдущая запись не завершена, новых чтений в этом направлении нет.
  В расширенном профиле не готовятся UDP-маршруты и не резервируются
  UDP-буферы или handshake-буферы для named backend.
* Backlog и пачка accept остаются по 32. При полном бюджете accept закрывает
  лишний сокет до handshake. В расширенном профиле обработчик за обход
  продвигает максимум 32 готовых клиента и продолжает со следующего слота
  на другом обороте epoll. Поиск готовых/свободных слотов остаётся линейным.
  Лимиты control (8), поколений (8), слушателей (16 опубликованных + 16
  подготавливаемых) и пачек завершений не увеличены.
* Проверка старта: soft `RLIMIT_NOFILE >= 2*N+128`, т.е. **328 / 2128**.
  Запас для control, слушателей, поколений и переходных FD; процесс не
  поднимает лимит сам. Это нижняя граница запуска, а не гарантия свободных
  FD при произвольных унаследованных дескрипторах.
* За пределами opt-in сохраняются отдельные лимиты: у named VLESS TCP —
  32 backend streams; у named SOCKS — 32 pending opens; у HY2 inbound —
  8 QUIC-соединений и 32 flow на слушатель; у HY2 outbound — 16 flow на
  профиль. Общий UDP-бюджет Full — 8 receive slots, 256 КиБ upload, 64
  пакета. У WG свои допуск, привязка и жизненный цикл устройства.

### Измерение

Один native Linux x86_64, GCC 13.3, ядро 6.8.0-149, CPU 0,1, soft/hard
NOFILE 4096. Два входа 50:50, числовой loopback direct, persistent state на
tmpfs. На каждый профиль отдельный PID; Apply и повторное заполнение — в том
же PID. Синтетическая цель задерживает ответы, пока **от каждого из N разных
TCP-соединений** не получит полный маркированный кадр (5003 байта payload).
Клиенты затем проверяют эхо побайтно. Три таких барьера: до Apply, на тех же
сокетах после Apply и на полностью заново набранной группе. Штатные профили
проверяются на 32, без повторения старого перебора на 100/1000 попыток.

| Профиль / N | RSS idle → N → release, КиБ | PSS idle → N → release, КиБ | FD idle → N → после Apply¹ → release | Apply idle / под передачей, мс |
|---|---:|---:|---:|---:|
| Nano / 32 | 2668 → 3572 → 3716 | 955 → 1796 → 1940 | 20 → 84 → 88 → 20 | 0,507 / 0,956 |
| Full / 32 | 3156 → 4120 → 4248 | 1443 → 2344 → 2472 | 23 → 87 → 94 → 23 | 0,653 / 3,100 |
| Full / 100 | 3144 → 4700 → 4700 | 1431 → 2924 → 2924 | 20 → 220 → 224 → 20 | 0,659 / 0,397 |
| Full / 1000 | 3116 → 14940 → 14940 | 1403 → 13164 → 13163 | 20 → 2020 → 2024 → 20 | 0,747 / 4,602 |

¹ Все N ещё живы, удерживаются два поколения. `N` — снимок на полной ступени
после первого барьера, не непрерывный максимум. RSS/PSS из `smaps_rollup`
только процесса core, без драйвера, echo и памяти сокетов ядра. Число FD
включает служебные FD; штатный Full также поднимает datagram runtime.

На 1000 потоках прирост относительно своего idle — **11 824 КиБ RSS и
11 761 КиБ PSS** против 964 и 901 КиБ у штатного Full на 32. FD вернулись к
исходному числу, но RSS после закрытия остался 14 940 КиБ; после второго
заполнения и освобождения — те же 14 940. Слоты живут до остановки хоста;
освобождённые malloc-блоки не обязаны немедленно вернуть страницы ОС.
По этим снимкам нельзя приписать весь остаток одному типу объектов.

На каждой ступени по одному лишнему соединению на **каждом** входе отказано
до первого байта успеха. В одном принятом потоке получатель временно перестал
читать. На 1000 отправитель остановился после 6 619 136 байт, пока остальные
999 потоков обменивались данными; четыре STATUS заняли 0,839–3,743 мс,
Apply опубликовал ревизию 3. После возобновления чтения все 16 МиБ прошли с
проверкой. Это одна задержка Apply под нагрузкой на ступень, не p99, SLA или
оценка максимального throughput. Измерение не переносится на flash-хранилище,
named matrix, роутер или другую ABI.

### Воспроизведение

Из корня core, задать `SDK`, `PROTOCOLS` (пины ниже), `LIB` (каталог native
`libngtcp2.a`, `libwolfssl-server.a` и их `.cflags` с server/time-safe профилем
Full). Нужны GCC, Python 3.9+, Linux `/proc`, util-linux, iproute2 и права на
создание namespaces/mount. Перед запуском убедиться, что доступны CPU 0,1.

```sh
R=$(mktemp -d /tmp/opencode/direct-tcp.XXXXXX)
make -C experimental/provider CC=gcc BUILD="$R/bin" SDK="$SDK" PROTOCOLS="$PROTOCOLS" \
  NGTCP2_LIB="$LIB/libngtcp2.a" WOLFSSL_SERVER_LIB="$LIB/libwolfssl-server.a" \
  "$R/bin/steer-prototype-hy2-wg-netns" >"$R/build-full.log" 2>&1 &&
make CC=gcc NANO=1 NANO_BUILD="$R/nano" NANO_SDK="$SDK" NANO_PROTOCOLS="$PROTOCOLS" \
  nano >"$R/build-nano.log" 2>&1 &&
taskset -c 0,1 sh experimental/provider/direct_tcp_budget_test.sh \
  "$R/bin/steer-prototype-hy2-wg-netns" "$R/nano/steer-nano" >"$R/run.jsonl" 2>"$R/run.err"
```

Пины приёмки: `plugin-sdk` `fa2b823d928f6bdd3f1b4a533a0b2cb874b4f4dd`,
`steer-protocols` `ff827a1ce5b736a66c4027da659e7d4f91048385`, база core
`fe636fd`. Стенд сам создаёт отдельные net/PID/mount namespaces с единственным
`lo`, затем запускает обе стороны с UID 65534. Результат — четыре строки
отрицательных проверок запуска и четыре строки измерений, включая отдельные
снимки с закреплённым поколением и после повторного освобождения.
