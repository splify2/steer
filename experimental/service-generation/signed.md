# Подписанное дерево Full UI: установка, снятие и замена поколения

В профиле `steer-lab-signed-full/1` один **лабораторный** владелец ведёт диск,
запускает UI и принимает решение о смене дерева. Даже для первой публикации
нужен ответ живого владельца. Имя `steer-ui`, версия, порт и сохранённый
успешный ответ сами по себе не дают права переименовать каталог.

## Независимая проверка

Из корня core, на Linux x86_64 с возможностью создавать mount/PID/net namespaces:

```sh
sh experimental/service-generation/check-signed.sh "$UI" "$S2P" "$LIBS_DIR"
```

`UI` — checkout `6195d89589f347c15538c64fb2179cafdd9f7225` с соседними
`steer` и `plugin-sdk`; `S2P` — сборка `plugin-sdk/cmd/s2p`; `LIBS_DIR` —
штатная shared-сборка `steerd` от базы `047d944` (runtime `544b31a`) и её
`libsteer*.so.*`. Нужны статическая libc, Python 3.11+, `setpriv`, `ip`,
user xattrs и интерфейсы Linux из [проверки владельца](README.md). Тестовый
предок должен иметь возможность вызвать `pidfd_getfd` для собственного потомка.

Стенд с нуля собирает **Full `service-host`**, не foreground-вариант. У двух
поставок одинаковые имя, версия `0.0.0`, ELF и оригинальные assets; отличается
подписанное описание в `plugin.json`. Ключ издателя одноразовый, секрет
уничтожается до запуска владельца. Офлайн-каталог входных архивов доступен
владельцу только для чтения. Исходное распакованное тестовое дерево и сборка
удаляются. Владелец, UI и штатный менеджер при проверке работают под UID 65534.
В сеть namespace выведен только `lo`.

Положительный результат — последняя JSON-строка с `result: PASS`, привязками
двух поставок, точками обрыва и исходом гонки. В частности проверяются:

* Неверный ключ и изменённый payload при исходной подписи: отказ **штатного**
  проверяющего, до регистрации G. Запуск настоящего процесса сверяется по
  `/proc/<известный PID>/exe` и аргументу `--assets`; от этого UI по HTTP
  получены байты CSS и кириллического шрифта установленного дерева. Адрес
  берётся у сокета уже опознанного процесса. Поиска PID по порту нет.
* `SIGKILL` до и после переноса проверенного stage, при снятии и между
  двумя `rename`, после переноса замены до commit и после commit до ответа.
  Убитый владелец с остановленным `SIGSTOP` старым UI: при рестарте новый
  владелец видит терминальный запрет, но не получает свободную аренду и
  не может снять дерево. После выхода UI повтор даёт квитанцию.
* Параллельные remove/reinstall с одной квитанцией: фиксируется ровно одна
  операция. Ответ `fence(A)` оставляют **непрочитанным в сокете** до запуска B;
  попытка снять B по этому ответу получает `stale-generation`. Переустановка
  проверяется также для побайтно того же архива с новым G и другим inode.
* Подстановка копии дерева с теми же байтами, изменение CSS, ссылка на соседа,
  путь вместо G, исчезновение запечатанного конца журнала. При отказе не
  удаляются пакет и свидетельства. PID/журнал независимого одноимённого UI
  и пользовательский файл вне пакета сохраняются.

## Что хранится до первого запуска

`signed.py --signed-full-prefix P init` публикует **новый** приватный префикс
и возвращает `prefix_id`; `serve` берёт исключительную блокировку этого типа.
Другие типы не усыновляются. Корень, `history`, файлы блокировок и три каталога
`stage`, `slot`, `retired` закреплены локально по пути, владельцу, режиму,
mount и dev/inode. G имеет вид `prefix_id:uuid` из двух 32-значных hex.

Аргументы операций передаются одним JSON-массивом. Например, `stage [G,D]`
выбирает архив **только по SHA-256** из тестовой поставки. В новом случайном
`--managed-prefix` штатный `plugin install --file` проверяет частную копию
архива с единственным доверенным ключом роли plugins. Он выполняет обычные
проверки `.s2p`, в том числе подписи исходных байтов MANIFEST, состава,
размеров, режимов и SHA-256 файлов. Этот префикс служит только для распаковки;
его реестр не виден ни одному планировщику. Манифест пакета файловый: связь
`steer-ui/full-ui → bin/steer-ui-service + assets` фиксирует **отдельный профиль**,
не произвольное поле `prog` и не `steer.services` штатного загрузчика.
Проверяются разрешённое множество файлов и отпечаток именно доверенной сборки
service-host: гарантия аренды зависит от исполняемого кода.

`prepare` связывает G с SHA-256 архива, ключа, точных байтов MANIFEST, сводным
хэшем имён/режимов/размеров/байтов **всех** файлов, версией, dev/inode
проверенного корня и единственным допустимым слотом `slot/full-ui`. Затем
именно этот inode перемещается в `stage/<uuid>`; `bind` запечатывает регистрацию.
Обе записи предшествуют публикации. Процесс запускается из `P/slot/full-ui`,
с путём assets внутри него и отдельным `--core-control`. При выходе и при
рестарте контроллера повторный запуск проходит через ту же проверку истории
и фактического дерева.

## Как происходит смена

| Операция | Условие и результат |
|---|---|
| `admit [G]` | Только до первой установки: нет предшественника, G проверен и связан, аренда свободна. Квитанция привязана к **этому** кандидату. |
| `fence [A]` | A — последний зафиксированный G. В журнале запечатывается необратимый запрет; прямой ребёнок остановлен и аренда свободна. Выдаётся квитанция именно для A и его binding. Потеря ответа допускает повтор. |
| `switch [A,B,R]` | Установить B вместо ожидаемого A. Для первой установки A = `null`, R из `admit`. Для снятия B = `null`. После снятия A остаётся последним поколением: пустое место нельзя принять за новую установку. |

Клиент до передачи запроса сверяет `SO_PEERCRED` с владельцем POSIX-блокировки
данного префикса. В ответ включены запрос с одноразовым вызовом и PID владельца.
Клиент сверяет квитанцию с запечатанной историей. Непредсказуемая часть
квитанции действительна у выдавшего её процесса до commit/его смерти; с диска
она не восстанавливается. **Точка сериализации** — один обработчик под
исключительной блокировкой владельца: сравнить ожидаемый tip и квитанцию,
снова получить аренду ребёнка, записать `intent(A,B)`, проверить фактическое
дерево, выполнить `renameat2(NOREPLACE)` и запечатать `commit`. Конкурирующий
обработчик не может вставить reinstall между сравнением и `rename`.
Во время замены A переносится в `retired/<uuid-A>`, затем B из
`stage/<uuid-B>` в освободившийся слот. Это **два** переименования с явным
промежуточным состоянием; сервис B недоступен планировщику до commit.
Снятие выводит дерево из слота, но сохраняет его в карантине. Сборки мусора,
рекурсивного удаления по запросу и очистки пользовательской конфигурации нет.

## Разбор прерванной операции

`status` обращается к владельцу. `inspect` локально **только читает**, не
выдаёт квитанций; при конкурирующей записи снимок лучше повторить через
`status`. `tip` — последний зафиксированный G (даже после снятия), `live` —
пакет по последнему commit, `slot` — фактический G в слоте прямо сейчас.

| Наблюдение | Следующий допустимый шаг |
|---|---|
| `preparing` | Повторить `stage` с теми же G и digest. Если перенос ещё не произошёл, штатно проверить архив вновь; если произошёл — сверить точное дерево. Другой архив под этим G не принимается. |
| `fenced`, без квитанции | Дерево остаётся. Получить новый `fence(A)` у действительного владельца; `previous-child-not-excluded` означает, что снятие пока невозможно. |
| `pending-switch` | Допустим только исходный `intent(A,B)`. Проверить расположение и отпечатки, вновь получить `fence(A)` (для первого G — `admit(B)`), повторить `switch`. Уже выполненные переносы не повторяются. |
| `active` / `removed` после потери ответа | Сверить `tip`, `slot` и `locations` с ожидаемым результатом. Потеря ответа не отменяет commit. |
| `recover-log` | Есть одна целая, но ещё не запечатанная запись. Владелец может завершить её после проверки диска. |
| `refused/recovery-blocked` при `inspect` | Например, потеря части запечатанной цепочки, чужой inode или байты, лишняя запись, недопустимая комбинация каталогов. Автоматического выбора «новейшего», сброса истории, переименования или удаления нет. |

Доверяем единственному кооперативному писателю, ядру Linux и конкретному
host, который не демонизируется и удерживает аренду до выхода. Не защищаемся
от враждебного процесса с тем же UID/root или согласованного отката всего
диска вместе с печатью. Проверены процессные обрывы, не потеря питания.
Профиль ограничен 32 поколениями; после обрыва проверки могут остаться
неисполняемые временные каталоги вне префикса. Они не становятся кандидатами
на запуск или автоматическое удаление.

**Остаток до production:** штатный `supd` по-прежнему может построить список
служб из другого реестра, и его fork/respawn/reload не проходят через этот
журнал и аренду. Также его штатный менеджер не сравнивает G и этот binding
при замене каталога. Для общего install/remove нужны единый протокол именно
между этими двумя штатными компонентами, охват холодного старта и всех
альтернативных писателей, а также стратегия для установок без ранней истории.
Файловый `--managed-prefix` и 2.x не получают права на service install/remove.
