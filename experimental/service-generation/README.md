# E4: кто может исключить следующий запуск Full UI

**Лабораторный результат, не установщик служб.** На core `136198e` у штатного
supervisor нет долговечного запрета `fork` для поколения плагина. Поэтому у
`steerd` нет нового CLI или разрешения `remove`. Здесь один контроллер сам
владеет **всеми** стартами одного фиксированного `steer-ui/full-ui`. Стенд
запускает настоящий Full `steer-ui-service` из UI `6195d89`. У независимого
соседа такое же имя службы, но другое пространство ID и другой владелец.

## Почему требуется другой контракт

* В 2.x `src/daemon/helpers.c` строит список из `plugin_svc_at`, а
  `src/daemon/supd.c` ведёт и перезапускает детей. Манифест и видимый реестр
  сегодня не содержат истории тех ID, которые supervisor видел раньше.
* UI `6195d89:src/ui_host.c` использует явный `--core-control` для v3 и
  `STEER_EVENT_FD` для событий владельцу. При потере читателя UI выходит,
  когда процесс сможет исполняться. `ready` сообщает об открытии HTTP; ни
  `ready`, ни закрытый PID, ни успех `disable` не запрещают следующий старт.
* В отклонённых `e4caf0e`/`94b63d7` запрет и ожидание остановки связаны с
  действующим supervisor и арендой запроса; снимок `/proc` и уточнение
  личности интерпретатора не запрещают старт после снимка или рестарта.
  Эти изменения не интегрированы. Ядро v3 не является владельцем UI-процесса.

## Граница и порядок операций

`controller.py --service-generation-prefix P init` создаёт **только новый** `P`
одним `renameat2(RENAME_NOREPLACE)` из частного временного каталога.
Лабораторный путь — `/tmp/e4-lab-*/NAME`, родитель принадлежит UID, режим
0700. Для `serve`, `reserve`, `publish`, `fence`, `status` opt-in повторяется.
У `init` результат `prefix_id`; вызывающий выбирает новый случайный UUID для
попытки установки. Полный ID поколения — `prefix_id:uuid`, оба компонента
по 32 hex. Его нужно сохранить и передавать повторно, а не вычислять по
текущей версии пакета. `init` не усыновляет даже пустой `P`. Нет имён
штатной раскладки 2.x, импорта `state.json` или конверсии файлового профиля.

1. **`reserve G`: зарегистрировать до видимости.** В журнал попадает ID
   префикса, службы и поколения (связь через корневой отпечаток). Никакого
   старта из `reserve` нет. **`publish G`** — отдельное явное решение
   сделать это поколение доступным планировщику; оно возможно только после
   подтверждённой записи `reserve G`. Это публикация для контроллера, не
   установка пакета или регистрация его в legacy loader.
2. **Старт, respawn после выхода и холодный старт владельца** проверяют тот же
   запечатанный журнал. Только последнее `publish` допускает `Popen`. Каждая
   запись содержит SHA-256 предшественника в вычислении своего отпечатка;
   `fsync` записи предшествует обновлению `user.steer_gen_head` на том же
   закреплённом inode, затем ещё `fsync`. `fence` не стирает `reserve/publish`.
   Полностью записанный единственный хвост поверх прежней печати — намерение,
   которое новый владелец может завершить; пропавший ответ нельзя трактовать
   как отмену. Короткая строка, нарушенный переход или потеря запечатанного
   хвоста — отказ; префикс не усекается и не переинициализируется.
3. **`fence G`: необратимо запретить.** Владелец в той же последовательной
   очереди сначала запечатывает терминальный запрет для G (в том числе для
   ещё не опубликованной резервации), затем останавливает только своего
   непосредственного ребёнка и ждёт его завершения. Каждый запуск наследует
   эксклюзивную `flock` на отдельном закреплённом inode. Родитель отпускает
   свою копию после fork/exec; старый ребёнок удерживает её даже при `SIGSTOP`
   и смерти родителя. Без получения свободной аренды положительной квитанции
   нет. Новый владелец не посылает сигналы предполагаемому сироте. После его
   выхода запрос повторяется. Аналогично нельзя зарезервировать замену, пока
   не исключён старый ребёнок.
4. Только **ответ на текущий `fence G`** связывает `excluded:true` с этим
   запросом, доменом, точным поколением, PID владельца и запечатанной вершиной
   истории. Клиент заново сверяет её с локальным журналом. Статус `fence` сам
   по себе не квитанция: запрет может уже действовать при ещё живом ребёнке.
   Повтор команды не снимает запрет. Новая установка требует другого G.
   Просроченный запрос к G не может выключить более поздний G′. Квитанция
   о G не разрешает удалять по общему имени `steer-ui` или по пути, который
   уже может принадлежать G′.

### Доказательство владельца

`type` связывает nonce, канонический путь, dev/inode корня и обязательных
файлов. Проверяются владелец, тип, режим, отсутствие жёстких/символьных
ссылок на файлы, mount ID, состав каталога, журнал и его печать. Supervisor
единолично держит **процессную** POSIX write-lock на `owner.lock` до выхода.
Клиент соединяется по частному abstract Unix `SOCK_SEQPACKET` в данном
netns; **до передачи запроса** сверяет UID/PID `SO_PEERCRED` с `F_GETLK`
именно этого inode. Команда и ответ идут по тому же fd и содержат случайный
одноразовый вызов. Это не авторизация по существованию сокета. У свободной
блокировки нет владельца; offline-ответа «можно удалить» нет. Не используются
legacy ctl, сканирование процессов или поиск UI по порту.

## Что проверено и как повторить

Linux x86_64, Python 3.11+, локальная ФС с user xattrs, POSIX locks, flock,
`renameat2`, `pidfd`, `SO_PEERCRED`. Нужны права организатора на namespaces.
Передать доверенные выходы сборок (не бинарник из устанавливаемого пакета):

```sh
# UI checkout 6195d89589f347c15538c64fb2179cafdd9f7225 и соседний plugin-sdk:
# make -C "$UI" service-host
sh experimental/service-generation/check.sh \
  "$UI_BUILD/steer-ui-service" "$UI/assets" "$LIBS_DIR"
```

`LIBS_DIR` — shared `steerd` для проверки разделения с `--managed-prefix`.
Контроллер и оба UI работают под UID 65534 в частных mount/PID/net namespaces;
в сети только loopback, порт выдаёт ядро. У каждого UI свой путь
`--core-control`; v3-сервер и трафик для этой проверки не нужны. События
`ready` не проверяются и не участвуют в решении. Реальность запуска сверяется
по известному PID и его `exe`.

Стенд убивает владельца до записи, после записи/до печати и после печати;
проверяет повтор, отмену резервации, переустановку и сохранение терминальных
записей. Ключевой отрицательный опыт: перезапуск после `SIGKILL` при
**остановленном `SIGSTOP` старом UI**. Новый supervisor уже владеет префиксом
и может запечатать запрет, но его собственная таблица детей пуста: пока старая
аренда занята, ответ только `previous-child-not-excluded`. После `SIGCONT`,
выхода старого UI и нового `fence` приходит квитанция. Холодный старт больше
не поднимает G. У соседа проверяются неизменные PID и байты истории. Отдельно
проверяются действительный respawn до запрета, чужой слушатель того же UID,
отсутствующий владелец, подмена inode блокировки и повреждение истории.

**Пределы.** Кооперативный доверенный UID и один путь запуска фиксированного
host, который не демонизируется, не передаёт аренду и не закрывает её раньше
выхода. Префикс и блокировки не защищают от враждебного процесса того же UID,
ручного обходного запуска, согласованной подмены снимка *вместе с печатью*,
отката часов/состояния VM или потери питания. Проверяются процессные SIGKILL.
Журнал ограничен 1 МиБ, при резервации оставляется место под завершение;
не предусмотрены сброс, ротация или перенос истории. Старые установки без
истории нельзя признать безопасными задним числом. До production install/remove
нужны интеграция всех путей запуска реального supervisor с этим запретом и
атомарное связывание удаления **конкретных байтов пакета** с G, включая
сериализацию замены. Этого права лабораторная команда не выдаёт.
