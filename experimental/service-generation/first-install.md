# E4: первичная установка подписанного Full UI

`steerd` умеет создать отсутствующий `supd-full/2` из одного локального
`.s2p`. Публикуется сразу весь домен, включая проверенное дерево, историю
и привязку. Установка не запускает UI. После неё тот же `steerd` умеет
запустить UI как владелец и [снять это поколение](remove.md).

## Вызов и свидетельство результата

```sh
# P=/tmp/e4-lab-…/subject, родитель уже существует, принадлежит UID и имеет 0700.
# Заранее сохранить случайный TX (32 строчные hex-цифры).
steerd --supd-full-prefix "$P" plugin install-first "$TX" \
    "$ARCHIVE" "$ARCHIVE_SHA256" "$TRUSTED_PUB" "$HOST_SHA256"
steerd --supd-full-prefix "$P" plugin confirm-first "$TX"
```

Архив и ключ задаются абсолютными каноническими путями. Ключ назначает
оператор **отдельно от поставки**; это единственный доверенный ключ данной
операции, а не ключ, обнаруженный в архиве. Путь к нему должен принадлежать
доверенным владельцам (root или текущий UID); сам файл не может быть доступен
на запись группе или остальным. Второй независимый вход политики —
SHA-256 разрешённого `service-host` сборки UI `6195d89`. Digest архива выбирает
конкретную поставку. Хеш кода, подсказанный самим непроверенным архивом,
не устанавливает доверия к коду.

Успех — код 0 и JSON `{"state":"installed","generation":G,"binding":B,"tx":TX}`.
Пара G/B годится для `remove-exact` с **новым** TX снятия. Только целый
успешный ответ подтверждает результат. При потере ответа повторить
`confirm-first` с сохранённым TX. Эта команда проверяет **текущее** ещё
активное поколение; после начала снятия она не выдаёт установочную квитанцию.

## Как получается один домен

1. `pmfirst.c` проверяет конечный путь в лабораторном профиле, UID и приватный
   каталог родителя. Кооперативные установщики берут неблокирующий `flock`
   на inode родителя. Существующий `P` любого типа, занятый TX и вложенная
   установка отвергаются. Для попытки эксклюзивно создаётся
   `parent/.first-TX/` (0700). В нём создаётся `new`, а не сам `P`.
2. Хеш проверяется на ограниченной копии архива (до 16 МиБ). Эти же байты
   через запечатанный `memfd` читает штатный `unpack_verified` в `pminst.c`:
   Ed25519-подпись MANIFEST проверяется до payload; файлы сверяются по
   именам, SHA-256, размерам и режимам. Для этой команды нет `--unsigned`,
   скриптов, установки в 2.x, сети или обращения к работающему демону.
   Проверяются ID, версия, архитектура и совместимость file-only метаданных.
3. C-проверяющий передаёт в построитель привязки хеши **из распаковки**,
   dev/inode файлов и корня дерева. Один разрешительный список у владельца
   и установщика: `steer-ui` 0.0.0 x86_64, 13 файлов, включая MANIFEST,
   подпись, лицензии, точные пути assets и шрифтов. Единственный ELF — 0755,
   остальные файлы — 0644, каталоги дерева — 0755. Сверяются реальное дерево,
   эталон ELF, UID, mount ID, единичность ссылок и отсутствие лишних объектов.
4. До выхода из stage присутствуют закреплённые lock-файлы, барьер `.lock`,
   `type` с **конечным** путём, случайным G и хешами архива и ключа,
   `history = start G\n`, печать `A`, точная привязка `/2`. Это разрешение
   будущего старта, а не заявление, что процесс уже работал. Файлы, каталоги
   и xattrs синхронизируются. В `parent/.first-TX/receipt` до публикации
   записываются G, B, TX и P; строка сама по себе **не** означает успех.
5. Перед единственным `renameat2(work,"new",parent,basename(P),RENAME_NOREPLACE)`
   применяется проверка активного домена тем же кодом, что у владельца.
   После переноса синхронизируются оба каталога и проверяются квитанция,
   реальные inode, `type`, история и привязка уже по конечному пути. Только
   тогда менеджер отвечает `installed`. После публикации установщик не пишет
   внутрь домена; стартует только `steerd daemon --supervise --supd-full-prefix P`.

| Момент обрыва | Что делать |
|---|---|
| До `rename` | `P` отсутствует. Ни неполный `new`, ни готовая запись `receipt` не дают `confirm` или права на запуск. Для новой попытки нужен новый TX. |
| После `rename`, при ошибке `fsync` или потере ответа | `P` может уже содержать **целый** домен. `confirm-first` синхронизирует каталоги и сверяет обе стороны свидетельства. Повторный `install-first` ничего не присваивает. |
| Свидетельство отсутствует, повреждено, относится к другому TX/P, дерево заменено или снято | Отказ. Не восстанавливать привязку из того, что сейчас лежит по имени `P`. |

Ни один повтор не переименовывает сохранённый `new` и не удаляет каталог
по общему имени. Каталоги попыток, включая остатки отказа/обрыва, приватны,
не являются запускаемыми префиксами и сохраняются для разбора. Автоматической
сборки мусора нет. Не удалять `receipt` принятой попытки, если требуется её
последующее подтверждение.

## Границы и воспроизведение

Предполагаются доверенный UID и кооперативные писатели, локальная ФС с
user xattrs, значимыми `fsync`, mount ID и `RENAME_NOREPLACE` в пределах
одного mount. Это не защита от произвольного процесса того же UID/root,
откатывающего одновременно домен и квитанцию. `SIGKILL` и инъекция `EIO`
проверяют процессные обрывы, не физическую потерю питания. Допускается
только x86_64 Linux с проверяющим в составе `steerd`. Для `/2` под musl
mount ID берётся через тот же UAPI-помощник, что у файлового менеджера;
при отсутствии подтверждённого ID — отказ. Назначение AArch64-архива
или запуск Full на AArch64 этим срезом не поддерживаются.

Из корня core, с shared-сборкой из `build/build-libs.sh`:

```sh
sh experimental/service-generation/check-signed.sh "$UI" "$S2P" "$LIBS" \
    --first-install >first.log 2>first.err
# Для x86_64 musl: неизменённый ELF, его настоящий загрузчик из сборочного образа.
sh experimental/service-generation/check-signed.sh "$UI" "$S2P" "$MUSL_LIBS" \
    --first-install-musl "$MUSL_LOADER" >first-musl.log 2>first-musl.err
```

Стенд создаёт приватные mount/PID/net namespaces; процессный тест — UID 65534.
Python подготавливает подписанные **входные архивы**, вызывает CLI и наблюдает
результат. `native_manager.py` в этом тесте отсутствует. Сквозная проверка
опознаёт дочерний ELF по inode, читает CSS и шрифт по HTTP и снимает тот же
G/B с проверкой inode карантина. Отдельно проверяются подпись, посторонний
ключ, испорченные байты, лишняя подписанная запись, режим файла, чужой ELF,
гонка двух архивов, подмена готового дерева, обрывы и потеря квитанции.
Файловый offline-префикс и `/1` остаются отдельными режимами. Замены G на G′,
update и in-place reinstall нет.
