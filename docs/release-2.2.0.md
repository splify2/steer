# Подготовка 2.2.0

База ветки `release/2.2.0` — тег `v2.1.4` (`70d11ebb`).
Выпуск и теги не публиковались. Исправления переносятся выборочно из
`3dbc2bf` ветки разработки 3.0.0; новая архитектура runtime/spec не переносится.

## Исправления и исходные сообщения

| Область | Изменение и проверка |
| --- | --- |
| helpers | Монотонные миллисекунды переведены с `long` на `int64_t`. Переполнение после 24,9 суток подтверждено; стенд проверен и настоящим 32-битным бинарником musl. Таймеры не вытесняют обработку событий. |
| Vision | DIRECT включается после полного кадра, включая padding. Регрессия воспроизводится на старом коде, исправленный тест проходит. |
| DNS | Новые таблица и правила принимаются одной операцией; ошибка загрузки сохраняет предыдущий рабочий снимок. Проверены повреждённые и оборванные обновления. |
| TLS / gRPC / XHTTP | Проверка порядка сообщений и CertificateVerify, KeyUpdate, ограниченная обработка post-handshake и заголовков HTTP/2. Размеры и смещения старых структур проверяются против v2.1.4. |
| Hysteria2 / QUIC | Потоковый разбор ответа, общий предел сборки UDP, освобождение по TTL, отказ отдельного устаревшего потока, резерв CID в размере датаграмм. Есть реальные QUIC, AEAD и sanitizer-стенды. |
| ARM | [#34](https://github.com/splify2/steer/issues/34): добавлена arm_cortex-a7. [#35](https://github.com/splify2/steer/issues/35): soft-float ARM собирается с явным запретом FP/NEON. Обе сборки проверены кросс-компилятором; запуск на физических роутерах ещё нужен. |

В splify2 26.11.6 исправляются сообщения об ошибках LuCI, удаление ранее созданных
списков с кириллицей, отображение ошибок индекса плагинов и ложный вывод о пустой
подписке, когда ядро посчитало только VLESS, а в подписке есть другие протоколы.
Соответствующее отображение ошибок индекса перенесено в Andromeda 26.11.2.

## REALITY и Xray 26.11.9

Сходные сообщения есть в [Steer #29](https://github.com/splify2/steer/issues/29)
и [splify2 #43](https://github.com/splify2/splify2/issues/43).
В апстриме обсуждались требования новых серверов к ClientHello и гибридному обмену:
[Xray #7259](https://github.com/XTLS/Xray-core/issues/7259),
[Mihomo #3476](https://github.com/MetaCubeX/mihomo/issues/3476).
Это возможная связь, а не установленная причина конкретного сообщения о Remnawave 3.4.6.

Локальный стенд использует собственную TLS-маскировку и одноразовые ключи, без чужих
подписок и серверов. С точным тегом Xray `v26.11.9` (`676eaf66`) кандидат успешно
выполняет REALITY-рукопожатие и передаёт данные. Тот же probe на исходниках `v2.1.4`
возвращает ошибку чтения после открытия транспорта, в том числе без переноса объекта
соединения в памяти. Конкретное сообщение «не может пройти проверку подлинности» и
конфигурация Remnawave не воспроизведены. Такой случай не объявляется закрытым.
Также проверен Xray main `4d0bfb4d` (три режима XHTTP поверх TLS и REALITY/TCP),
Hysteria main `7040c167` — прямое соединение, TCP/UDP, обфускация и восстановление.

## Повторение проверок

Основные входы: `make test`, `make ext-test`, `make protocol-test`.
Для расширенного прогона нужны исходники зависимостей из рецептов `build/wolfssl`
и `build/ngtcp2`; задаются `STEER_WOLFSSL`, `STEER_NGTCP2`, `XRAY`, `HY2_SERVER`
и `PLUGIN_SDK`. Отсутствующие внешние стенды печатают пропуск, который не равен проверке.

```sh
make protocol-test WOLFSSL_LIBRARY=/path/libwolfssl.a NGTCP2_LIBRARY=/path/libngtcp2.a
python3 tests/transportprobe_build.py --wolfssl-library /path/libwolfssl.a --output /tmp/transportprobe --sanitize
python3 tests/transport_interop.py --probe /tmp/transportprobe --xray /path/xray --network tcp --reality
python3 tests/transport_interop.py --probe /tmp/transportprobe --xray /path/xray
LIBS=build/libs-host HY2_SERVER=/path/hysteria sh tests/run-hy2.sh
```

Архивы wolfSSL/ngtcp2 должны сопровождаться `.cflags` своего рецепта сборки.
В Andromeda под Node 26 тесты запускаются с `NODE_OPTIONS=--no-experimental-webstorage`:
это отключает экспериментальный глобальный localStorage Node, мешающий jsdom.

Сжатие доменных списков в RAM, WARP latency и аппаратный offload из сообщений
пока не имеют подтверждённого исправления в этой ветке. Новые протоколы и возможности
3.0.0 в этот перенос не входят.
