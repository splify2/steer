# Gate E: v2 preflight and Linux LAN compatibility profile

There are two distinct targets. The loopback SOCKS preflight below still
blocks the LAN fixture. To run that fixture as a gateway, use the explicit
[`steer-linux-lan-compat-v1` profile](#linux-lan-compatibility-profile).

## Read-only loopback preflight

`tools/gate_e_preflight.py` inventories a deliberately small subset of v2 JSON
using the pinned `steer` CLI parser. It does **not** convert a spec, install
anything, call apply, or execute package hooks.

```sh
make build/steerd build/steer
python3 tools/gate_e_preflight.py --steer build/steer --spec /path/to/spec.json
```

The source is opened once without following symlinks and read into a bounded
byte snapshot. SHA-256 and `json.loads` inventory use those exact bytes; the
trusted CLI receives the same snapshot on stdin via
`steer spec convert --json --spec -`. Its normalized output is needed only to
detect parser defaults and is never included in the report. The CLI's stdin
mode is `LOAD_HUMAN` and does not execute plugin hooks. It runs with an empty
`PATH`, empty working directory, and isolated empty plugin-discovery roots.
YAML is rejected because exact source-level inventory is JSON-only.

The JSON report includes the CLI version, SHA-256 of the snapshot, whether the
source path still has the same regular-file identity/stat signature at the
final check, and generic semantic categories only. Deletion or replacement
during parsing is a controlled rejection. This final check is not a claim of
continuous immutability; bytes parsed and inventoried always come from the
single snapshot. The report never emits spec values, names, paths, credentials,
or parser diagnostics.
Exit codes:

- `0`: syntax accepted and only the conservative preflight subset was found;
- `1`: syntax accepted, but at least one semantic is blocking;
- `2`: parser/source inspection rejected the document or the input changed.

The target label is `linked-socks-v1-loopback`, not a general LAN router.
The only non-blocking configuration is an empty v2 document with no routes;
that is a no-op intent, not a LAN migration. The v2 parser's normalized output
is also inspected for implicit defaults. Explicit or implicit LAN capture,
legacy rules, interface/tunnel outputs, clients, lists and their external files,
DNS, `from_default`, advanced selectors, and unreviewed fields block. In
particular, LAN capture is never mapped to a loopback SOCKS inbound, and
`to: all` does not become a v3 SOCKS route. Unknown syntax rejected by the
legacy parser is a rejection, not a successful inventory.

Even exit code 0 means `preflight_subset`, **not migrated or convertible**:
`conversion_performed` remains false. This fixture is not the Linux installer,
backup, cutover, or offline rollback contract required by E4. The normal
preflight fixture invokes the actual v2.1.4 parser. An instrumented CLI test
captures its stdin, performs ordinary source replacement/deletion while
parsing, and verifies controlled rejection with no temporary source copy left
after completion.

The disposable supervisor acceptance test runs as an unprivileged user. It
installs an actual v2.1.4 `steerd` plus its legacy spec in a private prefix,
blocks that exact spec before pointer change, then independently installs and
starts the current v3 prototype with fresh v3 intent/state and a loopback SOCKS
echo. After rollback it starts the real v2.1.4 daemon against the returned
private state directory and verifies a Unix `ctl status` response. The
artifact-pair canary also verifies that missing or mismatched paired-state
metadata blocks rollback, while an independent fixture of the old
software-only `.manifest`/`.previous` layout (without `.state-format`) remains
rollback-compatible. The new WG journal is generated by the coordinator's
deterministic fake-backend codec fixture, not by a real kernel WireGuard device.
No systemd, nft, route or host service is involved.

### Cold LAN dataplane check after offline rollback

A separate Linux acceptance run on core `3cd31c0` exercised the restored
legacy **dataplane**, using the same offline bundle switcher. The v2.1.4
`steerd` was built from tag `70d11eb` (tested executable SHA-256
`b29153c6d150202f17e5ce4dc9e799f4d5dcb16c58120649cb640a61c07d2529`).
The sequence was:

1. Install that daemon with `tests/fixtures/gate-e/legacy-v2-lan.json` in a
   private prefix. In a fresh router netns, attach a separate LAN client on
   `br-lan` and a separate upstream host over a real kernel `wg0`. Configure
   the tunnel endpoints independently of Steer. Enable IPv4 forwarding and
   disable reverse-path filtering in the fixture router; its main table
   deliberately has no route to the echo destination. Confirm the TCP probe
   fails, then run `active/core apply --spec "$state/spec.json" --state-dir
   "$state"`. Check a WG handshake and byte-exact 4096-byte TCP echo from
   the LAN client. Tear down all three network namespaces.
2. In the same prefix, install the Full prototype with an **independent**
   v3 loopback SOCKS intent. Start it, verify a SOCKS echo and its persisted
   `config.json`, then stop it and run `bundle.py --prefix "$prefix" rollback`.
3. Verify selection of the original binary and state directory, the original
   spec bytes and the populated v2 mark/table registry. Recreate the network
   topology with fresh WG keys, empty nft ruleset and no fwmark rules.
   Repeat the failing pre-Apply probe, then Apply the **returned v2 state**:
   the WG handshake and a fresh 4096-byte LAN echo passed again. Registry
   bytes stayed identical and the v3 snapshot stayed in its own generation.

The empty second router rules out a pass from leftover forwarding rules or
an old tunnel session. This covers offline rollback followed by an explicit
v2 Apply. It does not convert LAN capture to v3, restore externally provisioned
WireGuard keys, or test automatic service startup.

Example from the repository root after building the two pinned binaries:

```sh
make -C steer/experimental/provider BUILD=/tmp/gate-e-build/v3 \
  SDK=/path/to/plugin-sdk PROTOCOLS=/path/to/steer-protocols \
  /tmp/gate-e-build/v3/gate-e-wg-journal-fixture
WGJ=$(runuser -u nobody -- mktemp -d /tmp/gate-e-journal.XXXXXX)
runuser -u nobody -- /tmp/gate-e-build/v3/gate-e-wg-journal-fixture "$WGJ"
unshare -n -- sh -c "ip link set lo up && runuser -u nobody -- python3 steer/tests/gate_e_supervised.py \
  /path/to/v2.1.4/build/steer /path/to/v2.1.4/build/steerd \
  /tmp/gate-e-build/v3/steer-prototype '$WGJ/linked'"
```

Local checks:

```sh
python3 tests/gate_e_preflight_test.py ./build/steer
python3 -m unittest discover -s experimental/offline-bundle -p 'test_*.py' -v
```

There is no `tests/gate-e-legacy-readonly.sh` in this checkout; the historical
reference was removed from the local-check list rather than pointing users to
a nonexistent test.

## Linux LAN compatibility profile

`experimental/offline-bundle/convert_lan.py` converts the **stopped private
generation** from the LAN fixture to a source-bound gateway plan. The selected
generation contains a one-shot Python launcher (`core`) and the real, separately
hashed `legacy-gateway-v2` executable. The latter is `build/steerd` from the
candidate checkout, **not** `steer-prototype`. It owns all packet classification,
nftables rules, marks, policy routes, legacy destination exclusions, family
defaults and failure handling. The launcher owns admission and lowers the plan
on each Apply. Linux and the operator own forwarding, firewall and `wg0`
(including peer keys, allowed IPs and return routes). No v3 provider or proxy
is in this datapath.

| Admitted input | Plan and effect |
| --- | --- |
| Explicit v2 JSON `lan.devices: ["br-lan"]` | Capture packets arriving from the LAN; no listener |
| Exactly one named `kind: interface, device: wg0` | Named external device egress, legacy default `on_fail: drop` made explicit |
| Exactly one named `to: all, out: <that ID>` | Keep rule ID and output reference; `all` has the legacy compiler's meaning |
| Registry `<output> 100000 300\n` | Preserve the existing hexadecimal mark and table, rather than allocate them again |

Only the default first allocation and lowercase ASCII identifiers matching
`[a-z][a-z0-9_-]{0,30}` are admitted. Extra fields, implicit LAN, duplicates,
other outputs/allocations, files, lists, plugins, clients, DNS and keys are
outside this slice. Both actual binaries must normalize the exact source
and the lowered candidate to the same document. `plan` rejects an active state
directory containing anything except `FORMAT`, `spec.json` and `registry`;
it is not an inventory of an arbitrary installed Linux system.

**Run the complete reproducer** from the candidate checkout, with the source
`steerd` built separately from tag `v2.1.4` (`70d11eb`):

```sh
make build/steerd
python3 -B tests/gate_e_lan_plan_test.py /path/to/v2.1.4/build/steerd build/steerd
sh tests/gate_e_lan_netns.sh /path/to/v2.1.4/build/steerd build/steerd
```

The second check requires Linux namespaces/mount privileges, iproute2, nftables,
WireGuard tools and kernel support. It creates its own PID/mount/net namespaces,
private `/etc`, `/run`, `/tmp` and `/var`, and disposable client/router/upstream;
there is no service installation. The prefix and both image inputs are local.
Python 3.9+, the OS tools, loader/libc and kernel are platform prerequisites,
not downloaded/bundled dependencies. The SDK and protocol providers are not
linked into this gateway mode.

Inside the isolated router the lifecycle is (invoke `convert_lan.py` and
`bundle.py` from `experimental/offline-bundle/` with `python3`):

1. With legacy writers stopped and after `down`, use `convert_lan.py plan
   --prefix "$prefix" --work "$work" --backend "$steerd"`. `work` must be a
   separate empty private directory. The active pointer stays put. `backup/`
   contains exact core, format, registry and spec bytes; `inventory.json` records
   their SHA-256, UID, GID, mode and original generation. Inspect
   `bundle/state/plan.json` (including the source SHA-256) and `manifest.json`.
2. `convert_lan.py switch` with the same arguments re-inventories the source and
   checks backup, staged artifacts and reviewed manifest under the bundle lock.
   It selects a new software/state pair, not new kernel rules. The candidate
   state contains the plan, registry and recovery inventory, **no source spec**.
3. `"$prefix/active/core" apply` lowers the sealed plan to a transient backend
   spec, verifies the external devices and invokes the bundled engine's real
   Apply. The launcher exits; Linux forwards subsequent packets. No daemon,
   watchdog, host boot registration or ongoing reconciliation is promised by
   this one-shot command. For a supervised daemon see below.
4. `"$prefix/active/core" down`, verify the dataplane is down, then
   `convert_lan.py rollback --prefix "$prefix"`. This profile-specific command
   checks the predecessor against the sealed backup inventory before selecting
   it; it needs neither staging nor the supplied backend. If old files drifted,
   it refuses the switch; inspect/restore from the private backup first.
   Get the returned state with `bundle.py --prefix "$prefix" state-dir` and
   run `"$prefix/active/core" apply --spec "$state/spec.json" --state-dir "$state"`.
   A pointer change by itself does not restore forwarding.

The regression uses the **same non-proxy LAN client and WG peers** throughout.
It checks no route before each Apply, byte-exact 4096-byte TCP echo, handshakes
and growing tunnel transfer counters. With a usable plaintext route in main,
it drops WireGuard UDP at the peer: the client fails, encrypted drops increase,
and zero plaintext TCP packets reach the alternate path. An uncaptured probe
from the router trips that same plaintext counter. Removing the fault restores
the client. After `down` and offline rollback, the old binary, spec and registry
match the originals and the client works again.

This is a cold, single-writer, private-prefix migration for **one** legacy
policy shape; acceptance covers IPv4 TCP. It is neither native managed spec v3
nor production E4. Hot cutover, automatic rollback across power loss, system
packages/services, inherited firewall policy, IPv6/UDP parity and any broader
inventory need their own acceptance. Before replacing this backend with a
native one, run the same client/negative control on that backend and demonstrate
equivalence of legacy selectors, exclusions, family and failure defaults.

### Private service switch and recovery

`experimental/offline-bundle/lan_service.py` is an optional foreground service
supervisor for this **same** sealed profile. Unlike the one-shot launcher, it
keeps the selected `steerd daemon --apply` alive. For the legacy generation it
starts `core` with the original spec; for the compatibility generation it
starts the manifest-verified `legacy-gateway-v2` with a lowered transient spec.
Both receive their actual paired `states/<generation>` and a private control
socket. The daemon itself performs boot Apply. No supervisor or client command
issues a separate Apply.

Reproduce the service gate (same binaries and Linux prerequisites as above):

```sh
sh tests/gate_e_lan_netns.sh --service /path/to/v2.1.4/build/steerd build/steerd
```

The wrapper creates an isolated PID namespace with its own procfs, nested
router mount/network namespaces, private writable OS paths, and two peers.
The trusted wrapper records the outer PID namespace for the service's startup
check. This is a dedicated, single-writer router; another daemon, firewall
manager or process editing the prefix is outside the contract.

Inside that router, prepare `convert_lan.py plan` against the stopped legacy
pair with its populated registry. The foreground supervisor then owns the
bundle lock for its lifetime. Commands below use `python3 lan_service.py
--prefix "$prefix"` followed by:

| Command | Result |
| --- | --- |
| `serve` | Start the selected pair; listen on the private `service.sock`. A cold start needs only the selected bundle, supervisor tools and external WG setup. |
| `status` | Query the live supervisor for `phase`, `selected`, `daemon_pid` and `detail`. A selected pointer alone is not readiness. |
| `upgrade --work "$work" --backend "$steerd"` | Block LAN forwarding, terminate/wait the old daemon, run its `down`, check kernel cleanup, revalidate the reviewed plan/backup, switch, and boot the candidate. |
| `rollback` | Stop/down the candidate under the same guard. Verify the previous binary/state inventory, switch and boot the previous daemon without staging or network fetch. |
| `stop` (or SIGTERM to `serve`) | Stop/down the pair; keep LAN forwarding blocked. Start a new `serve` for a cold service restart. |

The transfer guard is a separate nft `inet` forward chain dropping `br-lan`
traffic. It remains effective when either backend removes its own table. Only
after a clean starting baseline, live daemon control reply for the exact
spec/state paths, new `inet steer` table, expected fwmark rule and table 300
default route via `wg0` does the supervisor remove its guard. It does not
replace any steady-state legacy selector. Client reachability is tested
independently rather than inferred from the control socket.

An `upgrade` whose new daemon fails returns **nonzero**, even when verified
rollback and restart succeed: `phase=running`, `selected` points back to the
old pair and `detail` records the first failure. An uncertain stop/down,
changed predecessor or unsuccessful recovery yields `degraded`, not a direct
route or a search for some other binary. The supervisor attempts guarded
shutdown; if it cannot confirm guard/down it reports that uncertainty.
`service-state.json` records the last phase atomically; it is not a liveness
probe. A new `serve` refuses an unclean/degraded predecessor. Inspect this
record, the paired state, retained backup, children and kernel state; for
this fixture discard the disposable router and reprovision before retrying.
The one-shot tool and generic bundle CLI remain usable offline, but do not
clear a service stop guard in a running namespace.

The test exercises real bind failure on the candidate socket, recovery of the
original client without a manual Apply, successful upgrade, complete service
stop and cold restart with staging and input backend absent, explicit rollback,
and a missing external WG peer that prevents recovery. It verifies the daemon
executable/PID and state path, byte-exact TCP echo through WG and a calibrated
underlay counter with continuous LAN traffic during the transitions. This is
a controlled service lifecycle in a private namespace, **not** systemd or
machine boot. Power-loss recovery, adoption of orphan processes, host package
integration and full E4 remain open.
